# 롤토체스(TFT) 메타 정보 sLLM + RAG 서비스 브레인스토밍 (v2)

PRD 작성 전 조사 자료. 서비스 형태를 "**sLLM + RAG 기반 AI**를 구축하고, **웹사이트**로 정보를 제공하며, **챗봇**으로 사용자와 소통"으로 확정한 버전.

## 1. 서비스 정의

두 가지 접점을 동시에 제공하는 구조입니다.

- **웹사이트(정보 제공형)**: 티어리스트, 조합 상세, 아이템 빌드, 증강체 정보를 사람이 훑어보기 좋은 표/카드 형태로 제공. 반드시 LLM이 필요한 영역은 아니고, 정형 데이터를 그대로 렌더링하는 대시보드에 가까움.
- **챗봇(대화형)**: "지금 메타에서 뭐가 강해?", "이 아이템에 누가 어울려?" 같은 자연어 질문에 sLLM + RAG로 답변. 웹사이트 안에 위젯으로 내장하거나 별도 페이지로 제공 가능.

두 접점이 **동일한 데이터 계층을 공유**하는 게 핵심 설계 원칙입니다. 데이터를 두 번 만들지 않고, 웹사이트는 그 데이터를 표로 보여주고 챗봇은 그 데이터를 검색해서 자연어로 풀어주는 것뿐입니다.

이번 개발 범위에는 세 번째 기능으로 **사후 패인 분석(Post-game Review)**도 포함합니다 — 사용자의 최근 매치 데이터를 메타 데이터와 비교해 코칭 답변을 주는 기능. 자세한 흐름은 6-3 참고.

### 1-1. 웹사이트 vs 챗봇 역할 구분

근본적으로는 같은 데이터를 두 UX로 노출하는 것입니다 — 웹사이트는 "찾아서 클릭"(탐색형), 챗봇은 "물어보면 바로 답"(질의응답형). 다만 챗봇이 단순 지름길 이상의 가치를 갖는 지점이 있어, 두 채널의 역할을 아래처럼 나눕니다.

| 상황 | 더 적합한 채널 | 이유 |
|---|---|---|
| 전체 티어리스트/조합 목록 훑어보기 | 웹사이트 | 표·그래프로 시각적 탐색이 유리 |
| 복합 조건 질의 (예: "초반 강하면서 재사공 아닌 조합") | 챗봇 | 필터 여러 번 조작 대신 자연어 한 번으로 처리 |
| 여러 페이지(조합+아이템+증강체)에 흩어진 정보 종합 | 챗봇 | 페이지 이동 없이 하나의 답으로 결합 |
| 용어를 잘 모르는 초보 유저의 진입 | 챗봇 | 어떤 메뉴/필터를 써야 할지 몰라도 자연어로 질문 가능 |
| 특정 조합 상세 스탯/빌드 확인 | 웹사이트 | 정형 데이터를 정확한 표로 확인 |
| 맥락을 이어가는 후속 질문 (drill-down) | 챗봇 | "그 조합에 어울리는 증강체는?" 같은 대화 이어가기 |

즉 챗봇이 웹사이트를 대체하는 게 아니라, **브라우징은 웹사이트·구체적 질문과 정보 종합은 챗봇**으로 상호보완하는 구조입니다.

## 2. 데이터 소스별 실현 가능성 (업데이트)

### 2-1. op.gg MCP

`opgginc/opgg-mcp` (공식, MIT 라이선스). `https://mcp-api.op.gg/mcp`에서 이미 가공된 TFT 메타 데이터 제공.

- `tft_list_meta_decks`, `tft_get_champion_item_build`, `tft_list_item_combinations`, `tft_list_augments`, `tft_list_champions_for_item`, `tft_get_play_style`
- 가장 빠른 1차 데이터 소스. 단, README에 상업적 이용/재배포 조건이 명시되어 있지 않아 **op.gg에 직접 문의 필요**.

### 2-2. Riot 공식 API

TFT 전용 제품 등록·승인 필요. 원본은 매치 로그라 티어리스트는 직접 집계해야 함. 상업 이용은 조건부 허용(데이터 브로커 금지, 무료 티어 필수, 콘텐츠는 "transformative"해야 과금 가능).

### 2-3. MetaTFT — 실제 API 엔드포인트 확인됨

브라우저 네트워크 요청을 직접 열어본 결과, MetaTFT는 `www.metatft.com`이 아니라 별도 서브도메인 `api-hc.metatft.com`에서 데이터를 내려받는 구조였습니다.

```
GET https://api-hc.metatft.com/tft-comps-api/comps_stats
GET https://api-hc.metatft.com/tft-comps-api/unit_items_processed
GET https://api-hc.metatft.com/tft-stat-api/games?days=7
```

- 별도 인증 헤더 없이 단순 GET으로 JSON 응답 (CORS 열려 있어 서버사이드 호출도 가능)
- 응답에 `tft_set`, `queue_id`, `cluster_id` 등 메타 정보와 클러스터별 등수 분포(`places`), 표본 수(`count`) 포함
- **기술적으로는 접근 가능하지만, 공식 문서화된 API가 아닌 내부(비공식) 엔드포인트**입니다. robots.txt는 크롤링을 막지 않지만 이는 검색엔진 인덱싱 허용 여부일 뿐이고, ToS는 "플랫폼 데이터는 MetaTFT 소유"라고 명시하고 있어 상업적 재사용은 별도 허가가 필요할 가능성이 높습니다.

→ **결론: 기술적 장벽은 없다는 게 확인됐지만, 법적/약관 리스크는 그대로 남아 있음.** 서비스에 편입하기 전 MetaTFT에 이용 목적을 밝히고 허가를 구하는 절차를 권장.

## 3. 데이터 소스 비교 (업데이트)

| 소스 | 원본/가공 | 접근 난이도 | 상업적 이용 | 리스크 |
|---|---|---|---|---|
| op.gg MCP | 가공(완제품) | 낮음 (공식 MCP) | 확인 필요 | 상업 이용 조건 미확인 |
| Riot API | 원본 | 중간 (승인 절차) | 조건부 허용 | 승인 지연, 데이터 브로커 금지 |
| MetaTFT (api-hc) | 가공(완제품) | 낮음 (기술적으로 열려있음) | 불명확 | ToS상 무단 재사용 리스크 |

**권장:** op.gg MCP를 1차 소스, Riot API로 보완/검증, MetaTFT는 허가 확보 후 보조 소스로 편입.

## 4. 시스템 아키텍처

```
[데이터 수집] → [정규화/저장] → [공통 데이터 계층] → [웹사이트] / [챗봇(RAG+sLLM)]
```

### 4-1. 데이터 수집 계층
- op.gg MCP 배치 호출 (주기적, 예: 1일~수 시간 단위) — 메타 조합/아이템/증강체/빌드
- Riot API 보완 호출 (선택) — 랭크 상위 매치 샘플링, 최신 패치 즉시 반영용
- MetaTFT (허가 후) — 클러스터 통계 등 보조 지표

### 4-1b. 계정 연동 및 개인 매치 분석 모듈 (사후 패인 분석용)

- Riot ID(게임명#태그) 입력 → PUUID 변환·저장 (최초 1회, 이후 재사용)
- 분석 요청 시 Match-V1으로 해당 계정의 최신 매치 ID 조회 → 매치 상세(조합/아이템/증강체/등수) 가져오기
- 매치 데이터 vs 메타 데이터(RAG DB) 비교 로직: 조합의 메타 이탈도, 아이템 집중도, 증강체 시너지 여부 등을 계산해 코칭 근거로 사용
- 프라이버시: 같은 매치의 다른 플레이어 데이터가 함께 조회되는데, 익명 처리 안 된 상대 Riot ID는 노출 금지 (조합 정보 언급은 가능, 닉네임은 마스킹)

### 4-2. 정규화/저장 계층
- 챔피언/아이템/증강체 ID ↔ 한글명 매핑 (Data Dragon/TFT Assets)
- 모든 레코드에 `patch_version` 태깅 (구버전 데이터 혼입 방지 — 특히 오늘(7/29) Set 18 전환처럼 패치 경계에서 중요)
- 저장소: 구조화 DB(PostgreSQL) + 벡터DB(pgvector/Chroma, RAG 검색용 임베딩)

### 4-3. 웹사이트 계층 (정보 제공)
- 프론트엔드: 티어리스트/조합 상세/아이템 빌드/증강체 페이지 — 구조화 DB에서 직접 조회해 렌더링 (LLM 불필요, 빠르고 정확)
- 검색/필터 기능(패치별, 랭크별, 챔피언별)
- 페이지 하단 또는 사이드에 챗봇 위젯 삽입

### 4-4. 챗봇 계층 (RAG + sLLM)
- 사용자 질의 → 의도 분류(조합 추천/아이템 추천/증강체 추천/일반 전략 질문)
- 의도별 검색 쿼리 생성 → 구조화 DB/벡터DB 조회
- 검색 결과 + 질의를 sLLM 프롬프트에 결합 → 답변 생성 (근거 데이터·패치 버전 포함)
- 답변 내 웹사이트 상세 페이지 링크 첨부 (챗봇 → 웹사이트로 트래픽 유도, 상호 보완)

### 4-5. 공통 서빙/운영
- API 게이트웨이: 웹사이트용 조회 API / 챗봇용 대화 API 분리
- 캐싱(Redis): 동일 패치 내 동일 질문·페이지는 캐시로 비용 절감
- 모니터링: 패치 갱신 후 데이터 최신성 체크, sLLM 응답 품질 로깅

### 4-6. 데이터 적재(배치) vs RAG 검색(실시간) 시점 구분

혼동하기 쉬운 지점이라 명확히 구분합니다.

```
[배치, 주기적]  op.gg/Riot API 호출 → 정규화 → DB 적재     (패치 발생 시 / 하루 N회 등)
[실시간, 매 질문마다]  사용자 질문 → 이미 적재된 DB 안에서 검색(RAG) → LLM이 답 생성
```

- **데이터 수집은 배치**: 사용자가 질문할 때마다 op.gg/MetaTFT 외부 API를 직접 호출하지 않습니다. 그러면 응답이 느려지고, 외부 API 부하·rate limit 문제가 생깁니다. 미리 가공해서 DB(구조화 DB + 벡터DB)에 저장해두는 구조입니다.
- **RAG 검색은 실시간**: 사용자가 챗봇에 질문하는 그 순간, 이미 적재된 DB 안에서 관련 문서/레코드를 찾아 LLM 프롬프트에 넣는 과정은 매 요청마다 실행됩니다. 다만 "실시간 검색"이지 "실시간 외부 API 호출"은 아닙니다.
- **웹사이트는 RAG가 아님**: RAG는 "검색 결과를 LLM이 자연어로 풀어 답하는" 챗봇 전용 개념입니다. 웹사이트가 티어리스트/조합 페이지를 보여줄 때는 구조화 DB를 SQL로 직접 조회해서 표로 렌더링하는 일반적인 DB 조회이며, LLM이나 RAG 파이프라인을 거치지 않습니다.
- **캐싱**: 동일 패치 내 자주 나오는 질문("지금 메타 1티어 조합" 등)은 검색·생성을 매번 새로 하지 않고 캐시로 재사용 (4-5 공통 서빙/운영 항목과 연결).

## 5. sLLM/RAG 방향

핵심 판단 기준은 "데이터가 얼마나 자주 바뀌는가"입니다. 자주 바뀌는 데이터를 파인튜닝으로 가중치에 박아넣으면 재학습 비용·최신성 문제가 생기므로, TFT 데이터를 갱신 주기별로 계층화해서 RAG/파인튜닝/프롬프트 중 어디에 둘지 나눠야 합니다.

### 5-1. 데이터 계층별 처리 방식

| 계층 | 데이터 종류 | 갱신 주기 | 권장 방식 |
|---|---|---|---|
| Tier 0 (정적) | 게임 규칙, 용어 정의(증강체·재사공 등), 응답 톤/포맷 | 거의 안 바뀜 | 시스템 프롬프트 또는 경량 파인튜닝 |
| Tier 1 (저빈도) | 세계관/로어, 챔피언 기본 스탯(코스트·직업 태그), 아이템 조합 레시피 | 세트 단위 (~4개월), 가끔 패치 조정 | RAG 기본, 구조가 안정적이라 가벼운 파인튜닝도 가능 |
| Tier 2 (고빈도) | 티어리스트, 승률/픽률, 추천 조합·증강체·아이템 순위 | 패치 단위(2주) + 패치 내 실시간 변동 | **반드시 RAG.** 파인튜닝 절대 금지 |

- **Tier 2가 이 서비스의 핵심 가치**인데, 이걸 파인튜닝하면 (1) 2주마다 재학습 비용 발생, (2) 재학습 사이 기간엔 구버전 지식을 확신 있게 말하는 문제, (3) 구/신 버전 지식이 가중치 안에서 섞여 환각처럼 나타날 위험이 있음. RAG는 검색 문서에 `patch_version`을 붙여 출처·기준 시점을 답변에 명시할 수 있다는 장점도 있음.
- **파인튜닝의 역할은 "지식 주입"이 아니라 "언어 이해·톤 보정"으로 한정**: TFT 고유 용어 이해, 질문 의도 파싱(예: "이 아이템 누구 줘?" → 아이템 추천 의도), 답변 포맷 일관성. 오픈소스 sLLM은 TFT 전문 용어에 약할 수 있어 이 부분만 가볍게 LoRA로 보강하는 걸 권장.
- 프레임워크: LangChain/LlamaIndex 등으로 검색-생성 파이프라인 구성, 베이스 모델은 오픈소스 소형 모델(예: Qwen2.5-7B, EXAONE 등) 후보

## 6. 서비스 이용자 flow

### 6-1. 웹사이트 경로
1. 사용자가 티어리스트/조합 페이지 방문
2. 패치·랭크 필터 선택
3. 구조화 DB 조회 결과를 표/카드로 렌더링
4. 특정 조합 클릭 → 상세 페이지(빌드, 증강체 추천 등)
5. 궁금한 점은 페이지 내 챗봇 위젯으로 바로 질문 가능

### 6-2. 챗봇 경로
1. 사용자가 자연어 질문 입력
2. 의도 분류 → 최신 패치 기준 데이터 검색(RAG)
3. sLLM이 검색 결과 근거로 답변 생성 (티어/승률/추천 이유 + 패치 버전 명시)
4. 답변에 관련 웹사이트 상세 페이지 링크 제공
5. 후속 질문으로 drill-down (예: "그 조합에 어울리는 증강체는?")

### 6-3. 사후 패인 분석 경로

1. **계정 연동(최초 1회)**: Riot ID(게임명#태그, 지역) 입력 → PUUID 저장
2. **분석 요청**: 챗봇에 "방금 게임 분석해줘" 입력 또는 웹사이트 "최근 전적 불러오기" 버튼 클릭
3. **매치 데이터 조회**: Match-V1으로 최신 매치 ID 조회 → 매치 상세(조합/아이템/증강체/등수) 확보 (게임 종료 후 API 반영까지 짧은 지연 가능)
4. **메타 비교 분석**: 사용자 매치 데이터를 현재 패치 메타 데이터와 비교 (조합 이탈도, 아이템 집중도, 증강체 시너지)
5. **코칭 답변 생성**: sLLM이 비교 결과를 근거로 잘한 점·아쉬운 점·다음 게임 제안을 자연어로 생성
6. **결과 전달**: 챗봇에 요약 코칭 표시, 필요 시 웹사이트 상세 리포트 페이지(라운드별 등수 변화, 아이템 타임라인 등)로 연결

## 7. 호스팅/인프라 전략 (무료 vs 유료)

구성 요소별로 무료 가능 여부가 다릅니다. 결론부터: **MVP는 거의 무료로 구축 가능하나, sLLM 추론 부분에서 병목이 생김.**

| 구성 요소 | 무료 옵션 | 제약/주의사항 |
|---|---|---|
| 웹사이트 프론트엔드 | Cloudflare Pages, Vercel, Netlify | Vercel Hobby 플랜은 **상업적 이용 금지** 조항 있음 — 상업 서비스면 Pro 필요. Cloudflare Pages가 상대적으로 자유로움 |
| 백엔드 API(챗봇 API) | Render 무료 웹서비스(512MB RAM) | 미사용 시 슬립 → 콜드 스타트 지연(수 초~수십 초). 데모엔 괜찮지만 실사용자 응대엔 불편할 수 있음 |
| DB (구조화 + 벡터) | Supabase 무료 Postgres + pgvector, 또는 Qdrant Cloud 무료 티어 | 구조화 데이터와 벡터 검색을 하나의 무료 DB로 해결 가능 |
| 배치 데이터 수집(스케줄러) | GitHub Actions 무료 티어 | 주기적 크론잡으로 op.gg/Riot API 호출 → DB 적재 |
| sLLM 추론 | Groq, Hugging Face Inference Providers 등 오픈소스 모델 무료 API | **진짜 병목 지점.** GPU 추론은 무료 서버에 없음. 요청 수 제한 있음(예: Groq 무료 티어 분당 30회·일 1,000회 수준), 커스텀 파인튜닝 체크포인트는 못 올림 |

### 7-1. sLLM 추론 선택지

- **(A) 직접 파인튜닝한 커스텀 모델 자체 호스팅**: GPU 서버 필요, 사실상 유료(RunPod, Vast.ai 등 저가 GPU 임대라도 비용 발생)
- **(B) 파인튜닝 없이 무료 호스팅 API 그대로 호출**: Groq/HF Inference Providers 등 영구 무료 티어로 오픈소스 모델(Llama, Qwen 등) 사용. 5장의 "파인튜닝은 톤/용어 보정용으로만" 방향과 맞물려, 초기엔 프롬프트+RAG만으로 이 옵션을 쓰는 게 합리적

### 7-2. 권장 전략

1. **MVP 단계**: Cloudflare Pages(프론트) + Render 무료(백엔드) + Supabase 무료(DB+벡터) + GitHub Actions(스케줄러) + Groq 무료 API(LLM 추론) 조합으로 비용 거의 없이 구축
2. **트래픽 증가 또는 상업 서비스 정식 운영 시**: 백엔드는 유료 플랜(콜드 스타트 제거), 프론트는 상업 이용 허용 플랜, LLM은 유료 종량제 API 또는 자체 GPU 서버로 단계적 전환

## 8. 확장 아이디어 (이번 개발 범위 제외)

브레인스토밍 중 논의됐으나 이번 범위에는 넣지 않고 별도 트랙으로 남겨두는 아이디어입니다.

- **게임 중 보드 스크린샷 분석 코칭**: 사용자가 챗봇에 스크린샷을 올리면 분석해주는 기능. 일반 VLM은 작은 아이콘(챔피언 별 개수, 스택 아이템) 오인식 위험이 커서, CV 기반 아이콘 매칭(Data Dragon 스프라이트 대조)으로 구조화 데이터를 뽑은 뒤 sLLM에 넘기는 하이브리드 방식이 필요. 사후 패인 분석(Match-V1 기반)으로 상당 부분 대체 가능해 우선순위 낮춤.
- **게임 중 실시간 인게임 오버레이 코칭**: 완전히 별도의 제품 라인. 웹은 OS 차원에서 다른 네이티브 앱 위에 오버레이가 불가능하고, 모바일은 오버레이 권한이 있어도 TFT 모바일 클라이언트의 실시간 보드 데이터를 읽을 공식 API가 없어 사실상 불가능. Windows 데스크탑에서 Overwolf SDK(Riot이 화이트리스트한 TFT 게임 이벤트 API)를 활용하는 방식만 현실적이며, 지금 설계한 웹+챗봇 스택과는 별개의 네이티브 앱 개발이 필요함. 게임 메모리 직접 읽기 방식은 치팅 도구로 오인될 정책 리스크가 있어 피해야 함.

## 9. PRD 작성 전 확인이 필요한 사항

- op.gg API/MCP의 상업적 이용·재배포 조건 (직접 문의)
- MetaTFT `api-hc.metatft.com` 데이터 사용 허가 여부 (직접 문의, 확보 전까지는 서비스에 미편입)
- Riot Developer Portal TFT 제품 등록·승인 소요 기간
- 웹사이트 UI/UX 범위: 어떤 페이지(티어리스트/조합 상세/아이템/증강체)까지 만들지
- 챗봇 배포 형태: 웹사이트 내장 위젯 단독 / 디스코드봇 등 추가 채널 여부
- 무료 티어 설계 (Riot 정책상 필수 — Riot API를 조금이라도 쓴다면 적용)
- sLLM 베이스 모델 선정 (오픈소스 소형 모델 후보 비교 필요)
- 데이터 갱신 주기: 패치 단위(2주) vs 랭커 데이터 실시간 반영 여부, 웹사이트/챗봇 각각의 캐시 정책
- 초기 예상 트래픽/사용자 규모 (무료 티어로 버틸 수 있는 범위인지 가늠 기준)
- 커스텀 파인튜닝 필요 시점 (무료 호스팅 API로 시작 → 언제 자체 GPU 서버 전환할지 기준)
- 계정 연동 방식: Riot ID 수동 입력 vs RSO(Riot Sign-On) OAuth (보안·신뢰성 vs 구현 난이도 트레이드오프)
