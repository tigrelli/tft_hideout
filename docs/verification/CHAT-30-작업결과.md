- **TASK**: 미확정/미래 정보 환각 방지(생성 그라운딩 강화)
- **상태**: 완료(PM 확인 2026-08-19, 구현·자체검증·도커 재검증 모두 완료)
- **선행 TASK**: CHAT-01, CHAT-17, CHAT-18 (TEST-11 H15/E2/E9/E15/H18에서 발견, 2026-08-19 신설)
- **근거 문서**: `docs/verification/TEST-11-작업결과.md`(카테고리 H·E 결과 상세)
- **변경 파일**: `backend/services/web_search.py`, `backend/services/chat_stream.py`, `backend/services/prompt_assembly.py`, `backend/tests/test_chat30_content_grounding.py`, `backend/tests/test_chat17_web_search.py`(기존 fixture 보강)

## 문제

TEST-11 카테고리 H 채점 중 발견된 가장 심각한 유형 — 미공개·미확정 정보를 근거 없이 구체적으로 단정 생성. H15가 가장 심각(다음다음 세트를 "세트 15/소년만화 배틀물/2025년 말~2026년 초"로 단정). 기존 CHAT-18의 `verify_web_citation()`은 URL 존재 여부만 사후검증할 뿐, 본문 내용(세트 번호·날짜 등) 자체가 근거 없이 생성됐다는 더 근본적인 문제는 걸러내지 못함 — 실제로 H15의 인용 URL 자체가 할루시네이션이라 경고는 붙었지만, "세트 15"라는 본문 주장 자체의 근거 없음은 별도로 검증되지 않았다.

## 대상 5개 질문별 실제 조치

| 질문 | 실측 원인 | 조치 |
|---|---|---|
| **H15** | 검색 결과에 전혀 없는 세트 번호(15, 14)·시기를 구체적으로 단정, 인용 URL도 할루시네이션 | ✅ 코드 수정(본문 그라운딩 검증 신설) |
| **E9, E15** | 세트 번호 혼동(현재/과거 세트를 다른 세트인 것처럼 답변) — E15는 특히 "다음 세트인 세트 15"로 근거 없는 세트 번호를 구체적으로 언급 | ✅ 코드 수정(동일 검증이 세트 번호 불일치를 잡음), CHAT-29의 `[알려진 사실]` 규칙과 함께 이중 방어 |
| **H18** | 검색 결과에 없는 챔피언 이름 목록을 "커뮤니티·미검증 자료"로 라벨링하며 사실상 생성 | ⚠️ 프롬프트 규칙만 추가(목록 나열도 근거 없는 항목 금지) — 세트 번호·날짜처럼 결정론적으로 검증 가능한 형태가 아니라 코드 검증은 어려움 |
| **E2** | 실제로는 이미 공지된 정식 출시일이 있는데 "미공개"로 오답 — **환각이 아니라 반대로 검색 결과를 충분히 활용 못한 과소응답**(retrieval 품질 문제) | ❌ 이번 범위에서 다루지 않음(아래 한계 참고) |

## 구현

1. **`web_search.py`에 `verify_web_content_grounding()` 신설**: 답변에 등장하는 세트 번호(`세트\s*\d+`)와 명시적 날짜(`YYYY-MM-DD`, `YYYY년 M월`)를 추출해, 실제 검색 결과(title+content)에 하나도 없으면 `UNGROUNDED_CONTENT_WARNING`을 붙인다. `verify_web_citation()`(URL 검증)과 별개 함수로 분리해 두 검증이 독립적으로 동작(둘 다 걸리면 경고 두 개가 붙을 수 있음, 정보 손실 없음).
2. **`chat_stream.py`**: `_generate_web_search_answer()`에서 `verify_web_citation()` 다음에 `verify_web_content_grounding()`을 체이닝.
3. **`prompt_assembly.py`**: `WEB_SEARCH_SYSTEM_PROMPT`에 10번 규칙 추가 — "목록 나열도 1번 규칙(근거 없으면 추측 금지)의 예외가 아니다, 그럴듯한 이름을 지어내 채우지 마라"(H18 대응, 프롬프트 레벨).

## 자체 검증

- **pytest 신규 8건**(`test_chat30_content_grounding.py`): 검색 결과에 없는 세트 번호/날짜가 각각 경고를 발생시키는지, 검색 결과에 실제로 있는 세트 번호/날짜는 통과하는지(과잉 차단 방지 회귀), 세트/날짜를 언급하지 않는 평범한 답변은 그대로 통과하는지, 새 프롬프트 규칙 10번 문자열 확인, `generate_answer_stream` 스트림 레벨에서 조작된 세트 번호가 실제로 경고되는지와 정상 답변은 경고 없이 통과하는지.
- **기존 `test_chat17_web_search.py`의 mock fixture 1건 보강**: 새 그라운딩 검증이 생기면서 기존 테스트의 mock `WebSearchResult.content`("c")가 답변 속 날짜(2026-08-12)를 담고 있지 않아 새 경고가 잘못 붙는 문제를 발견 — 실제 프로덕션이라면 이 mock 자체가 비현실적(LLM이 근거 없이 날짜를 답한 것과 동일한 상황)이었으므로, mock content에 해당 날짜를 포함시켜 "실제로 근거가 있는 상황"을 정확히 표현하도록 수정(회귀 아님, 기존 테스트의 fixture 현실성 개선).
- **backend 전체 431/431 통과**(기존 423+신규 8건), ruff check/format 클린.
- **batch 전체 139/139 통과**(회귀 없음).
- Docker(test-db) 재검증 완료.

## 한계 및 후속 확인 필요 사항

- **H18은 코드로 결정론적으로 막지 못했다** — 챔피언 이름 목록처럼 정해진 패턴이 없는 자유 형식 콘텐츠는 세트 번호·날짜처럼 정규식으로 추출·대조하기 어렵다. 프롬프트 규칙(10번)만 추가했고, 실제로 얼마나 잘 지켜지는지는 배포 후 프로덕션 재질의로 확인 필요.
- **E2는 이번 범위에서 다루지 않았다** — 원인이 "환각"이 아니라 정반대(실제로 공지된 정보를 검색 결과에서 충분히 찾아내지 못해 "미공개"로 과소응답)라, 이 TASK의 anti-hallucination 안전장치로는 해결이 안 되는 성격이다. CHAT-29가 제외한 D8/D14와 같은 "검색 리트리벌 품질" 계열 문제로, 별도 검토가 필요하면 후속 TASK 후보로 남겨둔다.
- H15/E9/E15의 최종 답변 품질(정답지 채점기준 충족 여부)은 여전히 2차 Groq LLM이 새 프롬프트 규칙 10번·경고 문구를 실제로 얼마나 존중하는지에 달려있어, 배포 후 프로덕션 재질의로 최종 확인 필요(CHAT-27~29와 동일한 성격의 한계).
- `verify_web_content_grounding()`의 날짜 정규식은 `YYYY-MM-DD`/`YYYY년 M월(일)` 형식만 잡는다 — "2025년 말", "내년 초" 같은 모호한 시기 표현은 애초에 특정 가능한 "사실"이 아니라서 이 검증 대상이 아니다(모호한 표현 자체를 금지하는 건 프롬프트 규칙 2·3번의 몫).
