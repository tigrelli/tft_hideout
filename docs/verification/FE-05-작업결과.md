## 착수 중 발견한 문제 3가지와 PM 결정

FE-05를 실제 데이터로 완성하려는 과정에서 FE-03/FE-04와 유사한 패턴의 프로덕션 공백을 3가지 발견했다. 진행 방향은 PM에게 먼저 확인받았다("지금 같이 수정" 선택, 2026-08-05).

### 1. (가장 큰 문제) DATA-08/DATA-10이 완료 처리됐지만 `champion_item_builds`가 실제로는 한 번도 채워진 적 없음
`batch/normalize.py`의 `champion_item_build_rows()`(변환)와 `replace_champion_item_builds()`(저장)는 존재하고 각각 pytest로도 검증돼 있었지만, 실제 오케스트레이션 진입점인 `batch/run_patch_batch.py`가 이 두 함수를 한 번도 호출하지 않고 있었다(op.gg `tft_get_champion_item_build`는 챔피언 1명당 1회 호출해야 하는 도구라 다른 5개 도구처럼 `step_collect`에 그냥 끼워 넣을 수 없었던 게 원인으로 추정). 실제 운영 API(`GET /catalog/items/builds`)를 호출해보고 `builds: []`인 것을 보고 역추적하다 발견 — 개별 함수 단위 테스트만으로는 이런 "배선 누락"을 잡지 못하는 사례.

**수정**: `run_patch_batch.py`의 `step_collect()`에서 cdragon로 확인한 챔피언 목록(83명)을 순회하며 `opgg.get_champion_item_build(riot_champion_id)`를 호출해 `state["item_builds_by_champion"]`에 저장하고, `step_normalize()`에서 `champion_item_build_rows()` + `replace_champion_item_builds()`로 DB에 반영하도록 배선했다. 로컬 테스트 DB에 실제 op.gg+Community Dragon으로 전체 배치를 2회 실행해 검증(1회는 op.gg 쪽 일시적 네트워크 이슈로 `collect` 단계 실패 → 원자적 전환 설계(DATA-13)대로 승격 없이 안전하게 종료됨을 확인, 재실행 시 정상 성공): **54,289행, 83명 중 63명 챔피언에 빌드 데이터 생성 확인**(나머지 20명은 op.gg 표본 자체가 없어 챔피언명은 있으나 데이터 없음 — 정상 케이스).

### 2. API-04 스키마 버그: `item_combination`이 `dict`로 잘못 선언됨
FE-04에서 발견한 API-03 `recommended_items` dict/list 불일치와 동일 패턴. 배치가 실제로 저장하는 값(`entry.get("itemNames")`, op.gg 아이템 apiName 문자열 리스트)은 `list[str]`인데 Pydantic 모델은 `dict`로 선언돼 있었음(테스트 fixture도 실제와 다른 `dict` 형태를 써서 못 잡혔던 케이스). `list[str]`로 수정하고, `get_comp_detail`과 동일한 방식으로 `items` 테이블 조인을 추가해 `item_combination_names`(표시용 이름)와 `champion_name_kr`/`champion_name_en`도 응답에 새로 포함시켰다(기존에는 `champion_id` 정수만 줘서 프론트가 이름을 표시할 방법이 없었음).

### 3. (신규 발견, 실데이터 확인 후 판단) 챔피언 1명당 아이템 조합이 최대 1,735개까지 나옴
실제 op.gg 데이터로 검증하다가 챔피언 1명당 조합 수가 예상보다 훨씬 많다는 걸 발견(화면설계서 2.3 와이어프레임은 조합 1~2개짜리 예시만 보여줌). 전체를 다 내려주면 응답 크기·리스트 UX 모두 부적절하다고 판단해 SQL 윈도우 함수(`ROW_NUMBER() OVER (PARTITION BY champion_id ORDER BY play_rate DESC)`)로 **챔피언별 픽률 상위 10개(`TOP_BUILDS_PER_CHAMPION`)만 반환**하도록 캡을 추가했다(API-10이 대화 이력을 최근 3턴으로 제한한 것과 같은 성격의 판단). PM 확인 필요 시 이 상수만 조정하면 됨.

## 배포 및 운영 데이터 백필 (2026-08-05)

배포 확인: push 직후 Render(`GET /openapi.json`의 `ItemBuild` 스키마가 `item_combination: array`로 갱신됨 확인) · Cloudflare(`/items/builds` 200) 둘 다 정상 반영됨.

**`workflow_dispatch`로는 안 채워짐 — 원인 발견**: PM이 `patch-detection.yml`을 수동 트리거했으나 21초 만에 성공 처리되고 데이터는 그대로 비어있었음. 원인은 이 워크플로우가 "패치 버전이 바뀌었을 때만" 전체 수집·정규화(`step_collect`/`step_normalize`)를 실행하는 구조라서 — 운영 DB의 현재 패치(17.8)와 op.gg 최신 패치(17.8)가 같아 `run_patch_detection`이 `triggered=False`로 판단, `on_trigger()` 자체가 호출되지 않음. 즉 이번 스키마 변경처럼 "기존에 없던 데이터를 오늘 처음 채우는" 백필은 패치 감지 로직과 안 맞고, **다음 실제 패치 전까지는 아무리 재트리거해도 채워지지 않는 상황**이었음.

**해결(PM 승인 후 실행)**: 패치 감지·승격 로직은 건드리지 않고, 이미 pytest로 검증된 `champion_item_build_rows()`/`replace_champion_item_builds()`를 그대로 재사용하는 1회성 백필 스크립트(레포에 커밋하지 않음, 실행 후 삭제)를 운영 DB(`DATABASE_URL`)에 직접 실행. 운영 `champions` 테이블(읽기 전용)에서 현재 패치 챔피언 83명을 가져와 op.gg를 챔피언별로 호출하고 `champion_item_builds`(쓰기 전용, 다른 테이블 영향 없음)에만 반영 — filled=63, empty=20(로컬 검증과 동일 비율), failed=0.

**최종 확인**: `GET /catalog/items/builds` 630행(63명×상위10) 정상 응답, `/items/builds` 페이지 200. FE-05 완전히 종료.
