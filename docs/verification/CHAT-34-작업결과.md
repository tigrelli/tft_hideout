## 문제

D1("TFT 랭크 티어는 몇 단계로 나뉘나요?")에 정답 10단계 중 4개(아이언·브론즈·실버·골드)만 나열하고 "몇 단계"라는 질문 자체엔 답하지 않은 채 "자세한 정보 확인 안됨"으로 마무리. WBS는 CHAT-24가 다뤘던 gpt-oss-120b 리즈닝 토큰 소비로 인한 응답 절단(max_tokens 부족)과 유사한 원인일 가능성을 지목하며, **착수 시 먼저 실측으로 재현·원인 규명**을 요구했다.

## 조사 (실측 API 호출 6회)

1. **웹 검색 결과 확인**: D1과 동일한 쿼리로 실제 Tavily 검색을 재현한 결과, 두 번째 결과(imaeil.com 기사)에 "아이언, 브론즈, 실버, 골드, 플레티넘, 다이아몬드, 마스터, 그랜드 마스터, 챌린저 티어가 있다"는 **9개 티어명 전체가 이미 포함**돼 있음을 확인 — 검색 결과 자체는 불완전하지 않았다.
2. **동일 프롬프트로 실제 Groq API 4회 재실행**(현재 코드와 동일한 설정, `reasoning_effort` 미설정): **4/4 전부 `finish_reason="stop"`으로 9~10단계 전체를 완전하게 나열**하며 정상 답변. `max_tokens` 절단(`finish_reason="length"`)은 한 번도 관측되지 않음(completion_tokens 430~559, reasoning_tokens 323~462).
3. **`reasoning_effort="low"`로 낮춰 2회 재실행**(CHAT-24가 짧은 분류 호출에 적용한 값을 메인 답변 생성에도 적용해볼 목적): reasoning_tokens가 44~47로 급감했지만, **오히려 2/2 모두 답변을 포기하고 "해당 정보는 확인되지 않았습니다"만 반환** — 리즈닝을 줄이면 검색 결과를 종합해 답을 구성하는 능력 자체가 떨어지는 역효과가 실측 확인됨. 이 방향은 폐기.

## 결론 (PM과 논의)

D1은 **결정론적으로 재현 가능한 토큰 부족 버그가 아니라, reasoning 모델(gpt-oss-120b)의 확률적 변동**(가끔 목록 나열을 도중에 포기하는 경향)으로 판단 — TEST-11 A3/A11에서 이미 관찰된 "LLM 지시 준수의 확률적 한계"와 같은 계열. `reasoning_effort`를 조정하는 방향은 역효과가 확인돼 채택하지 않기로 PM과 합의하고, **관측된 최대 사용량보다 충분히 큰 방어적 `max_tokens` 상한만 추가**하기로 결정(정상 동작에는 영향 없이, 혹시 모를 폭주 케이스에 대한 안전망).

## 구현

- **`groq_client.py`의 `stream_groq_chat()`에 `max_tokens=1500` 추가**(`_MAIN_ANSWER_MAX_TOKENS` 상수, 실측 관측된 최대 completion_tokens 559 대비 충분한 여유). `reasoning_effort`는 건드리지 않음(메인 답변 생성 경로는 기존처럼 미설정 유지 — 위 조사에서 "low"가 역효과임을 확인했으므로).

## 자체 검증

- **pytest 신규 2건**(`test_chat34_max_tokens_safety_net.py`): `stream_groq_chat()`이 실제 Groq API 호출 시 `max_tokens=1500`을 전달하는지(mock 클라이언트로 호출 인자 검증), `reasoning_effort`는 여전히 전달하지 않는지(회귀 방지 — 향후 실수로 추가되면 답변 포기율이 높아지는 역효과가 재발할 수 있음을 문서화하는 테스트).
- **backend 전체 457/457 통과**(기존 455+신규 2건), ruff check/format 클린.
- **batch 전체 139/139 통과**(회귀 없음).
- Docker(test-db) 재검증 완료.

## 한계 및 후속 확인 필요 사항

- **이번 수정으로 D1의 확률적 실패가 사라진다는 보장은 없다** — 재현 자체가 안 됐고 원인이 reasoning 모델의 고유한 변동성이라, `max_tokens=1500` 안전망은 "혹시 모를 극단적 폭주 케이스" 방어일 뿐 D1이 관찰했던 "그럴듯하게 완결된 짧은 답변으로 스스로 포기"하는 패턴 자체를 막지는 못한다.
- 실측 4회 성공 사례가 우연히 운이 좋았을 가능성도 배제할 수 없어, 배포 후 D1을 여러 차례 재질의해 실패 빈도를 계속 관찰할 필요가 있다(재발 빈도가 유의미하게 높다고 확인되면 별도 TASK로 재검토).
- 다른 목록형 질문(예: 카테고리 A~C의 다단계 열거 질문들)에도 같은 계열의 확률적 실패가 있을 수 있으나, 이번 조사는 D1 하나만 표본으로 다뤘다 — TEST-11 전체 재실행 시 유사 패턴이 반복되는지 관찰 대상으로 남겨둔다.
